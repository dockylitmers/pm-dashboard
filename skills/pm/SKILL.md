# 외주 개발 PM

외주 프로젝트는 개발 속도만으로 일정이 정해지지 않는다. 고객사에서 받아야 할 자료·계정·정책이 늦거나, 계약서에 검수·지연 책임이 비어 있거나, 새 이슈가 처리보다 빨리 쌓이면 밀린다. 이 스킬은 PM이 이것들을 한곳에서 관리하게 한다.

## 도구

모든 일은 이 스킬에 들어 있는 CLI로 한다. Node 18 이상이면 되고 설치할 것은 없다.

```bash
node "${CLAUDE_SKILL_DIR}/scripts/pm.mjs" <명령> [옵션]
```

아래에서는 이것을 `pm`이라고 쓴다. `pm help`가 전체 명령이다. 사용자가 터미널에서도 쓰고 싶어 하면 `pm install-cli`로 `~/.local/bin/pm`을 만든다.

### PM 워크스페이스

PM 한 사람이 모든 프로젝트를 관리하는 폴더다. 보통 PM이 GitHub에 만든 **비공개** 저장소를 내려받은 곳이고, `pm setup`으로 만든다.

```
pm-workspace.json            공통 설정 (company: 회사 이름)
projects/<id>/project.json   일정·범위·체크리스트·요청 목록·계약·결정·위험
projects/<id>/docs/          요청 목록·킥오프 자료·주간 보고 초안 (--save)
projects/<id>/github.json    이슈 스냅샷 (pm sync, git에 올리지 않음)
```

`pm`은 지금 폴더에서 워크스페이스를 찾고, 없으면 `pm setup`이 등록해 둔 워크스페이스를 쓴다. 고객사 저장소에서 일해도 데이터는 워크스페이스에 쌓여서, 내부 메모가 고객사 저장소에 섞이지 않는다. `--project`를 빼면 지금 폴더의 git 저장소와 연결된 프로젝트를 쓴다.

워크스페이스를 바꾼 뒤에는 사용자에게 commit·push를 권한다. 직접 push는 사용자가 원할 때만 한다.

## 일하는 원칙

외주 PM이 고객사와 일하며 생기는 문제(왕복 질문, 책임 공방, 일정 오판)를 줄이려는 원칙이다. 답할 때도, 글을 쓸 때도 지킨다.

1. **결론 먼저.** 첫 줄에 답을 쓰고 근거는 그 아래에 둔다.
2. **공을 말한다.** 막힌 일은 누가 다음 행동을 해야 하는지(고객사·우리·개발팀)와 며칠째인지(D+n)를 같이 말한다.
3. **빈칸 대신 (제안) 값.** 고객사에 묻기 전에 아는 정보로 값을 채우고 "(제안)"이라고 표시한다. 고객사는 확인만 하면 된다.
4. **늦기 전에 요청한다.** 항목마다 필요 시점과 준비 기간이 있어 '언제까지 요청해야 하는지'가 계산된다. 그 날짜가 지난 것부터 말한다.
5. **예측은 범위로.** 예상일, 낙관~비관, 목표일에 남을 양을 함께 말한다. 처리 속도와 새 이슈 유입을 나눠 본다.
6. **보내는 것은 사람이다.** 고객사·팀으로 나가는 글과 GitHub·Notion 쓰기는 초안까지 만들고, 사용자가 확인한 뒤에만 실행한다.
7. **고객사에게 가는 글은 결론만.** 이슈 번호, 내부 메모, 코드 용어를 넣지 않는다.
8. **비밀값은 받지도 적지도 않는다.** 계정은 비밀번호 대신 개발사 계정을 권한 초대로 받는다. 비밀번호·API 키·고객 개인정보는 워크스페이스에도 적지 않는다.
9. **기록이 없다고 없는 것이 아니다.** 계정·콘솔·통화로 처리된 일은 문서에 안 남는 경우가 많다. 원본에서 찾지 못한 값은 '없음'으로 적지 말고 추정(`--guess`)으로 두고, 어디를 찾아봤는지와 함께 사용자에게 묻는다.
10. **값에는 확인한 날과 출처가 붙는다.** 값을 기록하거나 다시 확인할 때마다 `--src`로 어디서 확인했는지 남긴다. 오래된 값으로 보고하지 않는다.

## 처음 쓰는 PM: 워크스페이스 세팅

1. 사용자에게 GitHub에 **비공개** 저장소(예: `내아이디/pm-workspace`)를 만들어 내려받게 한다. 원하면 대신 만든다(`gh repo create <이름> --private --clone`, 실행 전 확인).
2. 그 폴더에서 `pm setup --company "회사 이름"`. 예전 데이터(`~/.pm-dashboard`)가 있으면 `--import ~/.pm-dashboard`.
3. 공개 저장소라는 경고가 나오면 비공개로 바꾸게 한다(`gh repo edit --visibility private`).
4. 첫 commit·push를 권한다.

## 새 프로젝트 (킥오프)

### 1. 등록

모르는 것만 짧게 묻는다: 이름과 id(영문 소문자), 고객사, GitHub 저장소(없으면 나중에), 개발 시작·마감, 고객사 QA, 출시일, **개발 범위**. 범위는 `pm scope --list`의 기능 중에서 고른다(앱·웹·관리자, 결제, 소셜 로그인, 문자·알림톡·메일·푸시, 회원 혜택, 콘텐츠, 고객센터, 상품 판매, 위치, 외부 연동). 견적서나 기능 목록이 있으면 읽고 범위를 제안한 뒤 확인받는다.

```bash
pm init <id> --name "이름" --client "고객사" --repo owner/repo \
  --scope app,admin,payment,social-kakao,alimtalk,push \
  --kickoff 2026-10-12 --dev-start 2026-10-26 --dev-end 2026-12-18 \
  --qa-start 2026-12-21 --qa-end 2027-01-08 --launch 2027-01-15
```

범위로 체크리스트와 고객사 확인 요청 목록이 정해진다. 범위가 바뀌면 `pm scope --add/--remove`. 진행된 항목은 건드리지 않고, 없어진 기능의 항목은 '해당 없음'이 된다. 그다음 `project.json`의 `summary`와 `channels.notion.url`(고객 요청 DB 링크)을 채운다.

### 2. 킥오프 4단계

`pm kickoff`가 단계별 진행과 이번 주 할 일을 보여 준다.

| 단계 | 끝난 것으로 보는 기준 |
|---|---|
| 계약 확인 | 계약서·견적서 확정, 범위 기준선 확정, 계약 점검 12항목 확인 |
| 범위·SRS | SRS, 일정 합의, 검수 기준, 변경 요청 절차를 받음·검토 이상 |
| 고객사 요청 | 고객사 확인 요청 목록의 모든 항목을 보냄 |
| 기본 세팅 | 담당자·소통 채널·보고 방식 확정, 저장소와 라벨·스프린트 준비 |

### 3. 계약 점검

계약서(또는 초안)를 사용자가 주면 읽고 12항목을 점검한다: 범위 부속서, 검수 방법·기간, 대금 단계와 검수 연결, 변경 요청 비용, 고객사 지연 시 일정 순연, 산출물·소스·계정 인도, 지식재산권, 하자 보수, 유지보수, 제3자 비용, 개인정보 처리 위탁, 해지·정산.

```bash
pm contract                                    # 현황
pm contract check delay-liability --status missing --note "고객사 지연 순연 조항 없음"
pm contract signed --date 2026-10-08
pm contract pay 착수금 --status paid
```

`ok`(있음)·`risk`(불리·모호)·`missing`(없음)·`na`. 위험·없음 항목은 무엇을 어떻게 보완할지 한 줄로 제안한다. 법률 자문이 아니라 놓치기 쉬운 것을 점검하는 것이라고 밝힌다. 기준과 문구 예시는 `references/contract.md`.

### 4. 고객사 확인 요청 목록

외주를 맡긴 고객사에 "개발에 무엇이 필요한지"를 안내하는 목록이다. Notion 요청 페이지와 같은 모양이다.

| 분야 | 항목 | 확인/요청 내용 | 정보 | 비고사항 |
|---|---|---|---|---|

- **정보** 칸은 `• 라벨: 값` 입력 줄이다. 우리가 채운 **제안값은 분홍**, **고객사 답은 노랑**이다. 제안값의 날짜는 프로젝트 일정으로 채워진다.
- 일정상 먼저 필요한 분야에는 ⭐, 비고에는 회신 기한이 붙는다.
- 처음 보낸 뒤 추가로 보내는 것은 '추가 확인 요청 (날짜)' 구분 줄로 차수를 나눈다.

```bash
pm sheet                        # Markdown (메일·문서·Notion에 붙여 넣기)
pm sheet --format notion        # Notion 요청 페이지 형식 (분홍·노랑 배경)
pm sheet --only-new             # 아직 안 보낸 것만 (추가 확인 요청)
pm sheet --mark-sent            # 사용자가 보낸 뒤: 요청함으로 바꾸고 대기 일수 시작
pm answer business-info "상호(법인명)=○○" "대표자명=○○" [--confirm]   # 받은 답 기록
```

Notion에 올려 달라고 하면 Notion 도구로 `--format notion` 결과를 요청 페이지에 만든다. 고객사 소통 공간에 쓰는 일이라 **올리기 전에 내용과 위치를 보여 주고 확인을 받는다**. 고객사가 Notion에 노랑으로 적은 답을 읽어 오라고 하면 읽고 `pm answer`로 기록한다(비밀번호가 적혀 있으면 옮기지 않고, 권한 초대로 바꾸자고 안내한다). 작성 규칙은 `references/client-requests.md`.

### 5. 기본 세팅

```bash
pm setup-repo            # 만들 라벨·스프린트 마일스톤 계획만 보여 줌
pm setup-repo --apply    # 사용자 확인 뒤에만: 라벨(epic, descope, 확인요청, blocked)과 주 단위 스프린트(SP-01 · 10/26~10/30), QA, 출시 마일스톤 생성
```

일정 예측은 이 이름 규칙을 읽는다. 저장소가 이미 다른 규칙을 쓰면 `forecastConfig.sprintPattern`을 맞춘다. 자세한 것은 `references/setup.md`.

### 6. 킥오프 회의 자료

```bash
pm kickoff-kit --save              # 고객사와 함께 보는 판
pm kickoff-kit --internal --save   # 계약 점검·대금·위험이 들어간 내부 준비 판 (고객사에 보내지 않음)
```

개요·일정·소통 방식·검수와 변경 관리·고객사에 요청할 것(회신 기한 순)·첫 2주 계획·회의에서 정할 것이 들어 있다.

## 진행 중 프로젝트

| 사용자가 말하면 | 할 일 |
|---|---|
| "오늘 뭐부터 해?" | `pm sync`(저장소 있으면) → `pm refresh` → `pm status` → 결론 한 줄, 브리핑, 이번 주 할 일. 다시 확인할 값이 있으면 아래 '최신화'를 먼저 |
| "최신화해 줘", "이거 최신이야?" | 아래 '최신화' |
| "고객사 답 기다리는 거" | `pm list --status requested` → D+7 넘은 것부터 `pm request <item>`(리마인드 초안) |
| "○○ 정책이 없는데" | `references/client-requests.md`의 받을 곳·진행 방식을 정하고 `pm request <item>` |
| "마감 맞출 수 있어?" | `pm status --json`, `pm forecast --velocity/--inflow/--descope` (`references/forecast.md`) |
| "주간 보고 써 줘" | `pm report --save` (팀용), `pm report --client --save` (고객사용) |
| "SRS 만들어 줘" | `references/srs.md` |
| "대시보드 열어 줘" | `pm build --open` 또는 `pm serve --open` |
| "고객사에 공유할 화면" | `pm build --project <id> --client` → 사용자가 열어 보고 보낸다 |

### 최신화

프로젝트 데이터는 한 번 채우면 낡는다. 고객사 답, 결정, 콘솔 설정은 대시보드 밖에서 바뀐다. 항목마다 마지막으로 확인한 날과 출처(`checked`)가 있고, `pm refresh`가 다시 볼 것을 모아 준다.

- **추정**: 원본에서 직접 확인하지 못한 값(`--guess`). 담당자 확인 전이다.
- **확인 뒤 GitHub 이슈가 바뀜**: 항목에 적힌 이슈(링크, `internal`의 #번호)가 마지막 확인 뒤에 바뀌었다.
- **오래됨**: 끝나지 않은 항목을 14일 넘게 확인하지 않았다(아직 손대지 않은 새 항목은 빼고 요청 시작일로 챙긴다).

순서:
1. `pm refresh` (`--json`이면 이슈 상태까지 구조로 받는다).
2. GitHub이 바뀐 항목: 확인일 뒤의 이슈 코멘트(결정 코멘트)를 읽고 반영한다.
3. Notion 등 고객 소통 원본이 출처인 항목: 그 페이지를 읽어 고객사 답(노랑)과 댓글을 반영한다.
4. 직접 확인할 수 있는 것은 직접 본다(읽기만): 도메인 DNS, 로그인 시작 주소가 어느 프로젝트 키를 쓰는지, 공개 URL이 열리는지, 스토어 등록 상태.
5. 기록할 때: 값이 바뀌었으면 `pm answer <item> "라벨=값" --src "출처"` 또는 `pm set <item> --status ... --src "출처"`, 그대로면 `pm check <item...> --src "출처"`.
6. 남은 추정 값과 콘솔·계약·통화처럼 사용자만 아는 것은 **한 번에 모아** 묻는다. 항목마다 지금 적힌 값, 찾아본 곳, 무엇을 알려 주면 되는지를 한 줄로. 답은 `--src "PM"`으로 기록한다.
7. 보고: 바뀐 것, 아직 모르는 것, 그 때문에 막히는 일정.

대시보드에서도 항목을 열어 '지금 확인함'을 누르면 확인한 날과 출처가 남는다. 킥오프 화면의 '다시 확인' 거르기로 모아 볼 수 있다.

사용자가 결정을 내리면 `project.json`의 `decisions`에서 빼고 체크리스트·일정에 반영한다. 결정이 필요한 일은 권장안 먼저, 선택지 2~3개, 기한, 정하지 않으면 막히는 것을 적어 `decisions`에 둔다.

## 대시보드

| 목적 | 명령 |
|---|---|
| 내가 보기 (모든 프로젝트) | `pm build --open` |
| 화면에서 답·상태·계약 점검을 바꾸고 파일에 저장 | `pm serve --open` (127.0.0.1:4477) |
| 고객사에 공유 | `pm build --project <id> --client` |

화면은 오늘·킥오프 체크리스트·고객사 요청·일정·속도·이슈·리소스로 나뉜다. 고객사 공유본에는 '오늘'과 '개발 관련 요청사항'(보낸 항목)만 있고, 내부 메모·계약·결정·위험·이슈 제목은 **데이터에서 빠진다**. 대시보드의 리미는 키가 없으면 대시보드 데이터로 답하고, `serve`를 띄운 셸에 `ANTHROPIC_API_KEY`가 있으면 서버를 거쳐 Claude로 답한다.

## project.json을 직접 고칠 때

`pm` 명령으로 안 되는 변경(항목 추가, 결정·위험, 리소스, 날짜)은 파일을 직접 고치고 `pm validate`를 돌린다. 필드는 `references/data-model.md`.

- `need`, `fields`, `proposal`, `note`는 고객사 요청 목록과 공유본에 그대로 나간다. 결론만, 고객사 말로 쓴다.
- 이슈 번호, 담당자, 내부 사정은 `internal`에 쓴다. 공유본에서 빠진다.
- 값을 고쳤으면 `checked: { at, src }`도 고친다(`pm check`가 해 준다). 추정한 값이면 `guess: true`.
