# 외주 개발 PM

외주 프로젝트의 일정은 개발 속도만으로 정해지지 않는다. 고객사에서 받아야 할 자료·계정·정책이 늦거나, 새 이슈(내부 QA 버그, 변경 요청)가 처리보다 빨리 쌓이면 밀린다. 이 스킬은 그 두 가지를 같이 본다.

- **킥오프 체크리스트**: 무엇이 있고 무엇이 없는지, 지금 공(다음 행동)이 누구에게 있는지, 고객사 답을 며칠째 기다리는지
- **일정 예측**: GitHub 이슈로 처리·유입 속도를 계산해 예상 완료일을 범위로 말하고, 목표일을 맞추려면 무엇을 바꿔야 하는지 숫자로 보여 준다
- **대시보드**: 위 내용을 한 화면에 모은 로컬 HTML. 캐릭터 에이전트 '리미'가 들어 있고, 고객사 공유본을 따로 만들 수 있다

## 도구

모든 일은 이 스킬에 들어 있는 CLI로 한다. Node 18 이상이면 되고 설치할 것은 없다.

```bash
node "${CLAUDE_SKILL_DIR}/scripts/pm.mjs" <명령> [옵션]
```

아래에서는 이것을 `pm`이라고 쓴다. `pm help`가 전체 명령을 보여 준다.

데이터는 고객사 저장소가 아니라 사용자 PC의 `~/.pm-dashboard/`(환경변수 `PM_DASHBOARD_HOME`로 바꿀 수 있음)에 둔다. 내부 메모와 위험이 고객사 저장소에 섞이지 않게 하려는 것이다.

| 파일 | 내용 |
|---|---|
| `projects/<id>/project.json` | 일정, 체크리스트, 결정, 위험, 리소스, 승인 대기열. 사용자와 Claude가 고친다 |
| `projects/<id>/github.json` | 이슈·마일스톤 스냅샷. `pm sync`가 만든다 |
| `config.json` | 공통 설정. `company`(회사 이름)는 요청서 서명과 화면에 쓰인다 |

`--project`를 빼면 지금 폴더의 git 저장소(`github.repo`)와 연결된 프로젝트를 쓴다. 프로젝트가 하나뿐이면 그것을 쓴다.

## 일하는 원칙

이 원칙은 외주 PM이 고객사와 일하며 생기는 문제(왕복 질문, 책임 공방, 일정 오판)를 줄이려는 것이다. 답할 때도, 글을 쓸 때도 지킨다.

1. **결론 먼저.** 첫 줄에 답을 쓰고 근거는 그 아래에 둔다. 현황은 3~4줄 브리핑으로 시작한다.
2. **공을 말한다.** 막힌 일은 누가 다음 행동을 해야 하는지(고객사·우리·개발팀)와 며칠째인지(D+n)를 같이 말한다. 7일이 넘으면 리마인드를 권한다.
3. **빈칸 대신 (제안) 값.** 고객사에 묻기 전에 아는 정보로 값을 채우고 "(제안)"이라고 표시한다. 고객사는 확인만 하면 되고, 답이 없을 때 그 값으로 진행해도 되는지도 같이 묻는다.
4. **예측은 범위로.** "언제 끝나요?"에는 예상일, 낙관~비관, 목표일에 남을 양을 함께 말한다. 처리 속도와 새 이슈 유입을 나눠서 본다.
5. **보내는 것은 사람이다.** 고객사·팀으로 나가는 글은 초안까지만 만든다. 사용자가 읽고 보낸 뒤에 상태를 `요청함`으로 바꾼다. 이메일·메신저·이슈 코멘트를 직접 보내지 않는다.
6. **고객사에게 가는 글은 결론만.** 이슈 번호, 내부 메모, 코드 용어, "확인 필요" 같은 빈 표시는 넣지 않는다. 앱 푸시·문자·이메일처럼 고객사가 쓰는 말로 쓴다.
7. **원본은 한 곳.** 계약서·정책 문서·고객 답의 내용은 복사하지 않고, 위치(링크)와 상태만 기록한다. 비밀번호·API 키·고객 개인정보는 어디에도 적지 않는다.

## 작업별 절차

### 새 프로젝트 등록 (킥오프)

1. 모르는 것만 짧게 묻는다: 프로젝트 이름과 id(영문 소문자), 고객사, GitHub 저장소(없으면 나중에), 개발 시작·마감, 고객사 QA 기간, 출시일. 날짜를 모르면 비워 둔다.
2. 프로젝트를 만든다. 표준 킥오프 체크리스트 36항목이 들어간다. 설명을 위한 데모는 `--from sample`.
   ```bash
   pm init <id> --name "이름" --client "고객사" --repo owner/repo \
     --kickoff 2026-10-12 --dev-start 2026-10-26 --dev-end 2026-12-18 \
     --qa-start 2026-12-21 --qa-end 2027-01-08 --launch 2027-01-15
   ```
   처음이면 회사 이름도 정한다: `pm config company "회사 이름"`.
3. `project.json`의 `summary`와 `channels.notion.url`(고객 요청 DB 링크)을 채운다. 이 프로젝트에 없는 기능(결제 없음, 앱 없음 등)의 항목은 사용자에게 확인하고 `not_needed`로 바꾼다. 이미 받은 자료는 `received`/`confirmed`와 링크로 바꾼다.
4. `pm validate`로 점검하고, `pm sync`(저장소가 있으면) → `pm build --open`으로 대시보드를 보여 준다.
5. 없는 자료는 아래 '없는 자료 확보'로 이어 간다. SRS가 없으면 'SRS'로 간다.

체크리스트 항목의 뜻과 흔한 준비 기간(예: Apple 법인 계정 2주 이상, PG 심사 2~4주)은 `references/checklist.md`에 있다.

### 오늘 브리핑, 현황 질문

```bash
pm sync            # GitHub 저장소가 있으면 먼저
pm status          # 사람이 읽는 브리핑
pm status --json   # 숫자가 더 필요하면
```

결론 한 줄 → 브리핑 3~4줄 → 오늘 할 일(누가, 무엇을, 언제까지) 순서로 답한다. 스냅샷이 하루보다 오래됐으면 sync부터 한다.

### 없는 자료 확보 (예: 환불 정책이 없을 때)

1. `pm list --status missing`에서 항목을 찾는다. 없는 항목이면 `project.json`에 추가한다(형식은 `references/data-model.md`).
2. 두 가지를 정한다. 기본값이 맞으면 묻지 않는다.
   - **받을 곳**(`--receive`): `notion` 고객 요청 DB(기본, 고객 소통의 원본) · `drive` 파일 · `email` · `repo` 우리가 저장소 문서로 정리
   - **진행 방식**(`--mode`): `ask` 고객사가 만들어 보냄 · `draft` 우리가 (제안) 초안을 쓰고 확인만 받음 · `meeting` 회의 안건
   - 정책 문서(약관·처리방침·환불)는 고객사가 처음부터 쓰기 어려우므로 `draft`를 권한다. 계정·키처럼 고객사만 만들 수 있는 것은 `ask`.
3. 초안을 만든다. 요청함 상태인 항목이면 리마인드 문안이 나온다.
   ```bash
   pm request <item> --receive notion --mode draft --due 2026-10-17
   ```
   대시보드 승인 대기열에 넣으려면 `--queue`를 붙인다. 보내지는 않는다.
4. 초안을 사용자에게 보여 주고 고칠 곳을 반영한다. 사용자가 보냈다고 하면 기록한다.
   ```bash
   pm set <item> --status requested --log "Notion 요청 DB로 요청"
   ```
5. 답을 받으면 `--status received`(검토 중) 또는 `confirmed`와 함께 `--res-label`, `--res-url`로 원본 위치를 남긴다.

요청서와 리마인드 작성 규칙, 예시는 `references/client-requests.md`.

### 고객사 대기 정리, 리마인드

`pm list --status requested`로 대기 항목을 보고 D+7이 넘은 것부터 리마인드 초안을 만든다(`pm request <item>`). 리마인드에는 막히는 일정과, 답이 없을 때 진행할 (제안) 값을 넣는다. 여러 건이면 한 번에 보낼 수 있게 묶어서 보여 준다.

### SRS 만들기·보완

`references/srs.md`를 읽고 따른다. 요약하면:

1. 근거 자료를 모은다: 계약서·견적 범위, 회의록, 화면 설계, GitHub 이슈(`pm status --json`, `gh issue list`), 체크리스트의 정책·계정 항목
2. 9개 절(개요, 사용자와 역할, 기능 요구사항(FR 번호), 화면 목록, 정책, 외부 연동, 비기능, 검수 기준과 QA, 범위 밖과 변경 관리)로 초안을 쓴다
3. 줄마다 `확정` · `확인 요청`(고객 답 필요) · `제안`(우리가 채운 값) · `준비 필요`(고객사가 준비)를 표시한다
4. 저장할 곳은 사용자에게 묻는다(고객사 저장소 `docs/`, 공유 드라이브 등). 고객사에 보낼 문서라 비밀값·내부 메모는 넣지 않는다
5. 체크리스트의 `srs` 항목을 `received`로 바꾸고 위치를 남긴 뒤, '확인 요청' 항목만 모아 고객 확인 요청 초안을 만든다

대시보드에도 같은 구조의 'SRS 생성 도우미'가 있다.

### 일정 질문 ("마감 맞출 수 있어?")

```bash
pm status --json
pm forecast --velocity 30          # 처리 속도 +30% (인원 추가)
pm forecast --inflow -40           # 새 이슈 유입 -40% (QA 버그 분류·중복 정리)
pm forecast --descope 20           # 범위에서 20건 빼기
```

답은 이렇게 쓴다: ① 맞출 수 있는지(순항·주의·위험) ② 새 이슈가 멈출 때의 예상일과 범위 ③ 지금 추세면 목표일에 남는 양 ④ 맞추려면 무엇을 얼마나(필요 처리량, 유입 상한, 범위 조정). 유입이 처리보다 많으면 범위만 줄여서는 다시 쌓인다는 점을 짚는다. 계산 방식은 `references/forecast.md`.

### 대시보드

| 목적 | 명령 |
|---|---|
| 내가 보기 (한 파일, 모든 프로젝트) | `pm build --open` |
| 화면에서 상태를 바꾸고 파일에 저장 | `pm serve --open` (127.0.0.1:4477) |
| 고객사에 공유 | `pm build --project <id> --client` |

- `build`로 만든 파일에서 바꾼 상태는 그 브라우저에만 저장된다. 계속 쓸 거면 `serve`를 권한다.
- 고객사 공유본은 내부 메모·결정·위험·이슈 제목·승인 대기열·일정 예측을 **데이터에서 빼고** 만든다. 보내기 전에 사용자가 한 번 열어 보게 한다.
- 대시보드의 리미는 키가 없으면 대시보드 데이터로 답한다. `serve`를 실행한 셸에 `ANTHROPIC_API_KEY`가 있으면 서버를 거쳐 Claude로 답한다(브라우저에 키를 두지 않음).

### 결정·위험 기록

사용자가 결정을 내리면 `project.json`의 `decisions`에서 해당 항목을 빼고, 필요하면 체크리스트·일정에 반영한다. 결정이 필요한 일은 권장안 먼저, 선택지 2~3개, 기한, 정하지 않으면 막히는 것을 적어 `decisions`에 둔다. 위험은 `risks`에 `level`(high·mid·low), 내용, 대응을 적는다.

## project.json을 직접 고칠 때

`pm set`으로 안 되는 변경(항목 추가, 결정·위험, 리소스, 날짜)은 파일을 직접 고친다. 고친 뒤에는 `pm validate`를 돌린다. 필드 설명은 `references/data-model.md`.

- `note`, `need`, `proposal`은 고객사 공유본과 요청서에 그대로 나간다. 결론만, 고객사 말로 쓴다.
- 이슈 번호, 담당자, 내부 사정은 `internal`에 쓴다. 공유본에서 빠진다.
- 상태를 바꾸면 `history`에 날짜와 한 줄 기록을 남긴다(`pm set`은 자동으로 남긴다).
