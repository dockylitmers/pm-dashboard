# 킥오프 체크리스트

외주 프로젝트를 시작할 때 모아야 하는 자료·계정·정책 목록이다. `pm init`이 표준 36항목(`templates/project.json`)을 넣는다. 프로젝트에 맞게 항목을 빼거나(`not_needed`) 더한다.

## 상태와 공

| status | 뜻 | 다음 행동 |
|---|---|---|
| `missing` | 아직 아무도 요청하거나 만들지 않았다 | 요청서를 만들거나 우리가 초안을 쓴다 |
| `requested` | 고객사에 요청했고 답을 기다린다. `requested` 날짜부터 대기 일수를 센다 | D+7이 넘으면 리마인드 |
| `received` | 받았거나 초안이 있고 확인이 남았다 | 검토해 확정하거나 고칠 점을 요청 |
| `confirmed` | 끝났다. 원본 링크(`res`)가 있다 | 없음 |
| `not_needed` | 이 프로젝트에는 필요 없다. 준비율 계산에서 빠진다 | 없음 |

| ball | 뜻 |
|---|---|
| `client` | 고객사가 다음 행동을 해야 한다 |
| `us` | 우리(PM·회사)가 다음 행동을 해야 한다 |
| `dev` | 개발팀이 다음 행동을 해야 한다 |

공은 상태와 따로 본다. 예를 들어 `received`인데 우리가 검토해야 하면 `us`, 고객사 확인을 기다리면 `client`다.

## 분류와 항목

### 계약·범위
- **계약서·견적서**: 범위 다툼의 1순위 근거. 기능 목록이 들어간 최종 견적서가 있어야 범위 기준선을 잡을 수 있다.
- **개발 범위 기준선**: 견적서 기능 목록 또는 SRS. 기준선이 없으면 검수 때 버그와 변경 요청을 구분하지 못한다.
- **SRS**: `references/srs.md`. 없으면 우리가 초안을 만든다.
- **일정 합의**: 개발·고객사 QA·출시 날짜. 고객사가 확인한 기록을 남긴다.
- **검수 기준·하자 보수 기간**: "중대 버그 0건이면 통과" 같은 판단 기준과 출시 후 보수 기간.
- **변경 요청 절차**: 기준선에 없는 요청은 변경 요청으로 받고, 일정·비용 영향을 먼저 알린다.

### 소통·운영 방식
- **담당자·결정권자**: 실무 담당자와 최종 결정권자가 다르면 결정이 늦어진다. 둘 다 받는다.
- **고객 소통 채널**: 요청·답·합의를 남기는 곳 하나(예: Notion 요청 DB). 메신저 대화는 결론을 여기에 옮긴다.
- **정기 보고**: 주간 진행상황, 회의 주기.
- **이슈 트래커**: GitHub 저장소를 정하고 `pm sync`로 연결해야 일정 예측이 된다.

### 정책·법무
- **이용약관, 개인정보처리방침**: 앱 심사와 출시에 필요하다. 고객사가 처음부터 쓰기 어려우므로 우리가 (제안) 초안을 쓰고 고객사·법무가 확인하는 방식(`mode: draft`)을 권한다. 공개 연락처와 개인정보 보호책임자는 임시 값을 쓰지 않는다.
- **취소·환불 정책**: 유료 결제가 있으면 필수. 취소 시점별 환불 기준과 예외(노쇼, 부분 사용).
- **운영 정책**: 회원 등급, 포인트, 쿠폰 등 기능이 있을 때만.
- **동의 방식**: 필수 고지와 마케팅 선택 동의를 어디서 받는지.
- **사업자 정보·통신판매업 신고**: 앱·웹 하단 표시용.

### 계정·외부 연동 (준비 기간이 긴 것부터 요청한다)
| 항목 | 흔한 준비 기간 | 메모 |
|---|---|---|
| Apple Developer (법인) | 2주 이상 | D-U-N-S 번호 필요. 고객사 명의 |
| Google Play Console | 수일~2주 | 개발자 신원 확인 |
| 결제(PG) 계약·운영 키 | 2~4주 | 라이브 심사 뒤 운영 키 발급 |
| 문자 발신번호·카카오 알림톡 | 1~2주 | 발신번호 서류 인증, 카카오 비즈니스 채널·발신프로필 심사 |
| 도메인·DNS | 즉시~수일 | DNS 관리 권한을 누가 갖는지 |
| 클라우드·서버 계정 | 즉시 | 고객사 명의에 우리 관리자 초대 |
| 소셜 로그인 앱 | 수일 | 네이버는 검수 신청이 따로 있다 |
| 앱 푸시 | 즉시 | Firebase 프로젝트, iOS 푸시 인증 키 |
| 외부 공급사 운영 계정 | 공급사마다 | 운영 키와 콜백 등록 담당을 정한다 |

### 브랜드·콘텐츠
로고 원본(AI·SVG), 화면 설계, 앱 아이콘·스토어 이미지·설명, 운영 콘텐츠(공지·FAQ), 고객 발송 문안. 운영 콘텐츠는 출시 직전까지 테스트 문구로 남기 쉬우니 QA 전에 기한을 잡는다.

### 운영·출시
고객센터 운영 시간·연락처, 관리자 계정·권한, 실제 운영 데이터(상품·가격), 고객사 QA 계획·테스트 계정, 스토어 심사용 테스트 계정, 출시 방식(심사 통과 뒤 수동 출시 권장).

## 막는 일정 (`blocks`, `blocksDate`)

항목이 없으면 막히는 일정(예: "스토어 심사", "결제 개발")과 그 날짜를 적는다. 대시보드 건강도는 2주 안에 필요한데 없는 항목이 있으면 '주의'로 올린다. 고객사에 요청할 때 "왜 지금 필요한지"를 설명하는 근거도 된다.
