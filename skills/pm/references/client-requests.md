# 고객사 확인 요청 목록과 요청서

외주를 맡긴 고객사는 개발에 무엇이 필요한지 모른다. 개발 범위가 정해지면 필요한 자료·계정·정책·결정을 한 목록으로 안내하고, 답을 같은 곳에서 모은다. 왕복 질문을 줄이고, 회신이 늦을 때 "언제 무엇을 요청했는지"의 근거가 된다.

## 목록의 모양 (`pm sheet`)

Notion 요청 페이지와 같은 표 하나다.

| 칸 | 내용 |
|---|---|
| 분야 | 계약·범위, 소통·기본 세팅, 사업자·운영 정보, 정책·약관, 계정·외부 연동, 브랜드·콘텐츠, 운영·출시. 묶음의 첫 줄에만 쓰고, 일정상 먼저 필요한 묶음에 ⭐ |
| 항목 | 짧은 이름 |
| 확인/요청 내용 | 왜 필요한지 한 줄 + "개발 착수(10/26) 전에 필요" |
| 정보 | `• 라벨: 값` 입력 줄. 우리가 채운 제안값은 **분홍**, 고객사 답은 **노랑**. 예/아니오는 O/X |
| 비고사항 | 회신 기한, 참고 |

- 첫 차수 위에 안내 문구가 붙는다: 분홍은 제안값이니 맞으면 두고, 다르거나 빈 곳만 노랑으로 적어 달라, 계정은 비밀번호 대신 권한 초대.
- 처음 보낸 뒤 범위가 바뀌거나 새로 물을 것이 생기면 같은 표에 **'추가 확인 요청 (M/D)'** 구분 줄을 넣고 이어 붙인다(`pm sheet --only-new`). 구분 줄에는 "지금까지 받은 내용으로 미리 채웠으니 다른 부분만 고쳐 달라"는 문구가 들어간다.

## 형식

| 명령 | 쓰는 곳 |
|---|---|
| `pm sheet` | Markdown. 메일·문서·Notion에 붙여 넣기 |
| `pm sheet --format notion` | Notion enhanced markdown(`<table>`, `<span color="pink_bg">`, `<span color="yellow_bg">`). Claude가 Notion 도구로 요청 페이지를 만들 때 |
| `pm sheet --save` | 워크스페이스 `projects/<id>/docs/`에 저장 |

## 흐름

1. 범위를 정하면 목록이 생긴다(`pm init --scope`, `pm scope`).
2. 보내기 전에 제안값을 채운다. 아는 정보(견적서, 회의, 기존 사이트, 스토어 정보)로 `fields[].proposal`을 채우면 고객사는 확인만 하면 된다. 모르는 칸은 비워 둔다. "확인 필요" 같은 빈 표시는 쓰지 않는다.
3. 사용자가 목록을 고객사에 보낸다(Notion 요청 DB의 한 행, 메일 등). Claude가 Notion에 올릴 때는 **위치와 내용을 먼저 보여 주고 확인을 받는다**.
4. 보낸 뒤 `pm sheet --mark-sent` → 상태가 '요청함'이 되고 요청일부터 대기 일수를 센다.
5. 답이 오면 `pm answer <item> "라벨=값" ...`(검토 필요) 또는 `--confirm`(확정). 대시보드 '고객사 요청' 화면에서 항목을 눌러 적어도 된다. 고객사가 Notion에 노랑으로 적은 답은 Claude가 읽어 와서 기록할 수 있다.
6. 회신 기한이 지나면 리마인드(`pm request <item>`).

## 계정과 비밀값

- 계정은 **비밀번호를 받지 않는다.** 고객사 명의로 만들고 개발사 계정을 관리자로 초대하게 한다. 2단계 인증이 필요하면 가능한 담당자를 받는다.
- 고객사가 비밀번호나 키를 적어 보냈으면 옮기지 않는다. 권한 초대로 바꿔 달라고 안내하고, 받은 곳에서 지우도록 권한다.
- `pm answer`와 `pm validate`는 비밀번호·키처럼 보이는 값을 막는다.

## 원칙

1. **무엇을, 왜, 어디로, 언제까지.** 항목, 막히는 일정, 전달 방법, 회신 기한.
2. **빈칸 대신 (제안) 값.** 고객사는 "그대로 진행"이라고만 답해도 된다.
3. **결론만.** 법 조항 설명, 구현 메모, 이슈 번호, 코드 용어, 진행 상태 열은 넣지 않는다. 개발자만 알면 되는 규칙은 개발팀 채널로.
4. **고객사 말로.** 앱 푸시, 문자, 이메일, 카카오 알림톡.
5. **보내는 것은 사람이다.**

## 항목 하나의 요청서 (`pm request <item>`)

목록과 별도로 항목 하나를 급히 요청하거나 리마인드할 때 쓴다.

| 상황 | 받을 곳(`--receive`) | 진행 방식(`--mode`) |
|---|---|---|
| 정책 문서(약관·처리방침·환불) | `notion` | `draft`: 우리가 초안, 고객 확인 |
| 계정·키·권한 | `notion` | `ask` |
| 파일(로고, 계약서, 이미지) | `drive` | `ask` |
| 의견이 갈리는 결정 | `notion` | `meeting`: 회의 안건 |
| 우리가 정리하고 고객은 읽기만(SRS 등) | `repo` | `draft` |

요청함 상태인 항목은 리마인드 문안이 나온다(요청일, 막히는 일정, 회신 기한, 답이 없을 때 진행할 (제안) 값). 같은 항목을 세 번째 리마인드하게 되면 글 대신 회의 안건이나 결정권자에게 올리자고 제안한다.

## 개발팀에 전달할 때

고객사 답을 개발팀에 넘길 때는 팀원이 물은 순서대로, 결론만 짧게 쓴다. 원본(요청 DB의 답)의 위치를 같이 준다.
