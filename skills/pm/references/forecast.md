# 일정 예측

`app/js/forecast.js`가 계산하고, CLI(`pm status`, `pm forecast`)와 대시보드가 같은 코드를 쓴다. GitHub 이슈·마일스톤 스냅샷(`pm sync`)이 있어야 한다.

## 무엇을 세나

- **범위**: 열린·닫힌 이슈 중 `epic`·`descope` 라벨과 목표일 뒤 마일스톤의 이슈를 뺀 것. 라벨 이름은 `forecastConfig.epicLabel`, `descopeLabel`로 바꾼다.
- **목표일**: 남은 스프린트가 있으면 마지막 스프린트 마감(개발 마감), 없으면 출시 마일스톤. 스프린트·출시 마일스톤은 제목으로 알아본다(`forecastConfig.sprintPattern`, 기본 `^(SP|Sprint|스프린트)[-\s]?\d+`; `releasePattern`, 기본 `출시|release|launch`). 스프린트 시작일은 제목의 `m/d~`에서 읽고, 없으면 마감 4일 전으로 본다.
- **처리 속도**: 최근 7일 구간을 최대 4개 보고, 최근 구간에 가중치를 더 준 주간 평균 완료 수. `not_planned`·`duplicate`로 닫힌 것은 완료가 아니라 취소로 센다.
- **유입**: 같은 구간의 '새로 만든 이슈 − 취소'. 프로젝트 초기에 한꺼번에 등록한 이슈는 유입이 아니므로 `forecastConfig.baselineEnd`(기본: 개발 시작 + 3일)까지 만든 이슈는 뺀다.

## 결과

| 값 | 뜻 |
|---|---|
| 예상일 | 새 이슈가 더 없을 때 남은 이슈를 다 닫는 날(주말이면 다음 월요일) |
| 낙관·비관 | 예상 기간의 ±40% |
| 목표일에 남을 이슈 | 남은 이슈 − (처리 − 유입) × 남은 주 |
| 유입까지 감안한 완료 | 처리가 유입보다 많을 때만 계산된다 |
| 필요 처리량 | 남은 이슈 ÷ 남은 주 + 유입 — 목표일에 0으로 만들려면 |
| 상태 | 유입까지 감안해 목표일 안이면 순항, 새 이슈가 멈출 때만 맞으면 주의, 그것도 넘으면 위험 |

이번 스프린트는 지금까지의 근무일 하루 평균 완료 수로 마감 안에 끝나는지, 몇 건이 넘어가는지 따로 본다.

## 설명하는 법

1. 결론: "개발 마감(10/30)은 주의예요."
2. 범위: "새 이슈가 멈추면 10/19(10/15~10/21)에 끝나요."
3. 진짜 문제: "하지만 주 131건이 새로 들어오고 108건을 닫아서, 지금 추세면 10/30에 약 180건이 남아요."
4. 선택지(숫자로):
   - 처리량을 주 169건으로(+56%) — 인원 추가, 담당 재배분
   - 유입을 주 N건 이하로 — 내부 QA 버그 분류, 중복 정리, 출시 후로 미룰 것 표시
   - 범위 조정 — 출시에 꼭 필요하지 않은 이슈를 `descope`로. 단, 유입이 처리보다 많으면 범위만 줄여서는 다시 쌓인다
5. `pm forecast --velocity/--inflow/--descope`로 각 선택지의 결과를 보여 준다.

## 한계

- 이슈 수로 세므로 이슈 크기가 크게 다르면 틀린다. 큰 이슈는 쪼개야 예측이 맞는다.
- 스냅샷이 오래되면 틀린다. 하루 넘었으면 `pm sync`부터.
- 첫 스프린트가 1주가 안 지났으면 처리 속도를 계산할 수 없어 예측이 나오지 않는다.
