# SRS 만들기·보완

SRS(요구사항 명세서)는 개발 범위의 기준선이다. 기준선이 있어야 검수 때 "기준선과 다르면 버그, 기준선에 없으면 변경 요청"으로 나눌 수 있다. 고객사에 보내는 문서이므로 결론만 쓰고, 비밀값·계정 정보·내부 메모는 넣지 않는다.

## 근거 자료 (있는 것부터)

1. 계약서·최종 견적서의 기능 목록 — 범위의 1순위 근거
2. 킥오프·정기 회의록 — 합의된 결정
3. 화면 설계(Figma) — 화면 목록과 흐름
4. GitHub 이슈 — 기능 묶음(라벨·에픽·마일스톤)과 진행 상태 (`gh issue list --state all --limit 500 --json number,title,labels,milestone`)
5. 체크리스트의 정책·계정 항목 — 정책과 외부 연동 절
6. 고객 요청 DB — 고객사 답과 합의

근거가 없는 줄은 지어내지 않는다. 대신 `(제안)`으로 우리가 권하는 값을 쓰거나 `(확인 요청)`으로 고객사에 묻는다.

## 구조 (9개 절)

| 절 | 내용 |
|---|---|
| 1. 개요 | 목적, 플랫폼(앱·웹·관리자·서버), 용어(고객사 업무 용어 그대로) |
| 2. 사용자와 역할 | 비회원·회원·관리자 등 역할별로 할 수 있는 일 |
| 3. 기능 요구사항 | 기능 묶음마다 `FR-<영역>-<번호>`. 각 FR에 수용 기준(AC)을 1개 이상 |
| 4. 화면 목록 | 화면(라우트)별 목적과 상태(빈 상태, 오류) |
| 5. 정책 | 결제·환불·회원 등급·알림 발송·개인정보 보관. 체크리스트 정책 항목과 연결 |
| 6. 외부 연동 | PG, 문자·알림톡, 로그인, 공급사 API. 운영 계정 준비 여부 |
| 7. 비기능 요구사항 | 지원 기기·OS, 성능 목표, 보안, 개인정보 보관·파기, 접근성 |
| 8. 검수 기준과 QA | 고객사 QA 기간, 통과 기준, 하자 보수 기간 |
| 9. 범위 밖과 변경 관리 | 이번에 하지 않는 것, 변경 요청 창구와 절차 |

## 줄마다 붙이는 표시

| 표시 | 뜻 | 고객사가 할 일 |
|---|---|---|
| `확정` | 근거가 있고 고객사가 이미 동의했다 | 없음 |
| `확인 요청` | 고객사 답이 필요하다 | 답한다 |
| `제안` | 우리가 정한 값이다. 답이 없으면 이대로 개발한다 | 다르면 알린다 |
| `준비 필요` | 고객사가 자료·계정을 준비해야 끝난다 | 준비한다 |

문서 본문에는 `(확인 요청)`, `(제안)`, `(준비 필요)`처럼 괄호로 쓴다. 고객사 문서에 "확인필요" 같은 빈 표시만 남기지 않는다. 묻는 줄에는 우리가 권하는 값을 같이 쓴다.

## 순서

1. 근거 자료를 모아 위 구조로 초안을 쓴다. 기능 묶음은 이슈 라벨·에픽과 견적서 목록을 맞춰 정한다.
2. 저장할 곳을 사용자에게 묻는다(고객사 저장소 `docs/srs/`, 공유 드라이브 등). 여러 파일로 나눌 만큼 크면 절마다 파일을 나눈다.
3. 체크리스트 `srs` 항목을 `received`, 공 `client`로 바꾸고 위치를 남긴다.
4. `확인 요청` 줄만 모아 고객 확인 요청 초안을 만든다(`references/client-requests.md`). 돈·날짜·상태·권한·개인정보에 닿는 것부터 묻는다.
5. 답을 반영해 `확정`으로 바꾸고, 개발 마감 전에 기준선 판(날짜)을 고정한다. 이후 바뀌는 것은 변경 요청으로 다룬다.

## 이미 SRS가 있을 때 (보완)

- 9개 절 중 빠진 절을 찾는다.
- 이슈에는 있는데 SRS에 없는 기능, SRS에는 있는데 이슈가 없는 기능을 짝지어 본다.
- `확인 요청`·`제안`·`준비 필요`의 개수를 세어 고객사 확인이 얼마나 남았는지 보고한다.
