# 설계 — 외주 개발 PM 시스템

외주 개발 PM이 아침 5분 안에 "무엇이 위험하고, 공은 누구에게 있고, 오늘 무엇을 보내야 하는지"를 알게 하는 도구다. Claude Code 스킬(대화), CLI(기록·계산), 대시보드(한눈에 보기) 세 면이 같은 데이터를 쓴다.

## 1. 풀려는 문제

외주 프로젝트의 일정은 개발 속도만으로 정해지지 않는다.

- **정보가 흩어져 있다.** 이슈는 GitHub, 고객사 답은 Notion, 진행 보고는 메신저, 계약은 공유 폴더, 디자인은 드라이브, 심사는 스토어 콘솔에 있다.
- **지연의 상당 부분이 고객사 대기에서 생긴다.** PG 라이브 상점, 발신번호, 공급사 운영 키처럼 고객사만 준비할 수 있는 것이 몇 달씩 밀린다. 이런 항목은 이슈 트래커에 잘 보이지 않는다.
- **일정 예측이 감에 의존한다.** 처리 속도와 새 이슈 유입을 나눠 보지 않으면 "다음 주면 끝난다"는 말이 매주 반복된다. 내부 QA가 시작되면 버그 유입이 처리보다 많아지기 쉽다.
- **요청이 빈칸 질문으로 나간다.** 고객사가 무엇을, 왜, 언제까지 줘야 하는지 모르면 왕복이 늘어난다.

## 2. 목표와 비목표

| 목표 | 어디서 |
|---|---|
| 아침 브리핑 3~4줄로 오늘 할 일을 정한다 | `pm status`, 대시보드 '오늘', 리미 |
| 킥오프에 필요한 자료·계정·정책이 빠짐없이 모이고, 없으면 그 자리에서 요청서가 나간다 | 킥오프 체크리스트, `pm request` |
| 완료일을 범위로 예측하고, 맞추려면 무엇을 바꿔야 하는지 숫자로 본다 | `pm forecast`, 일정·속도 화면 |
| 고객사와 같은 화면을 본다 | 고객사 공유본(`pm build --client`) |
| 여러 프로젝트를 같은 방식으로 관리한다 | 데이터 홈 하나에 프로젝트 여러 개, 대시보드 프로젝트 전환 |

**비목표**

- 이슈 트래커나 고객 소통 도구를 대체하지 않는다. 원본은 각 도구에 두고, 위치와 상태만 모은다.
- 자동으로 발송하지 않는다. 외부로 나가는 글은 사람이 읽고 보낸다.

## 3. 설계 원칙

1. **결론 먼저.** 맨 위에 브리핑, 숫자와 표는 그 아래.
2. **공(ball) 추적.** 모든 준비 항목에 다음 행동을 할 쪽(고객사·우리·개발팀)과 대기 일수(D+n). 7일이 넘으면 리마인드.
3. **원본은 한 곳.** 링크와 상태만. 내용은 복사하지 않는다.
4. **빈칸 대신 (제안) 값.** 요청서에 아는 값을 미리 채우고 확인만 받는다.
5. **예측은 범위로.** 예상일, 낙관~비관, 목표일에 남을 양. 처리와 유입을 나눠 본다.
6. **사람이 보낸다.** 초안까지만 자동. 나가는 글은 승인 대기열을 거친다.
7. **같은 화면, 다른 깊이.** 고객사 공유본은 내부 데이터를 빼고 만든 같은 화면이다.
8. **고객사 저장소를 더럽히지 않는다.** PM 데이터는 사용자 PC의 데이터 홈에 둔다.

## 4. 구성

```
pm-dashboard (이 저장소, Claude Code 플러그인)
└─ skills/pm
   ├─ SKILL.md              Claude가 따르는 절차와 원칙
   ├─ references/           체크리스트·요청서·SRS·예측·데이터 형식
   ├─ scripts/pm.mjs        CLI (Node 18+, 의존성 없음)
   ├─ app/                  대시보드 (index.html + js/forecast·core·app·agent)
   └─ templates/            표준 킥오프 체크리스트, 데모 프로젝트

~/.pm-dashboard (데이터 홈, 사용자 PC)
├─ config.json             회사 이름
├─ projects/<id>/project.json   사람과 Claude가 고치는 원본
├─ projects/<id>/github.json    pm sync 스냅샷
└─ build/                  pm build 결과
```

```
사용자 ──대화──▶ Claude Code + 스킬 ──명령──▶ pm CLI ──읽기·쓰기──▶ project.json
                                                   └─ sync ──▶ GitHub API ──▶ github.json
사용자 ──브라우저──▶ 대시보드 ◀── pm build(파일) / pm serve(로컬 서버, 변경 저장)
                     └─ 리미 ── 내장 모드 / Claude(serve의 ANTHROPIC_API_KEY 또는 브라우저 키)
```

- **같은 계산을 쓴다.** `forecast.js`(예측)와 `core.js`(체크리스트 상태, 건강도, 브리핑, 요청서 문안)는 브라우저와 Node 양쪽에서 돈다. 터미널의 `pm status`와 대시보드의 숫자가 다를 수 없다.
- **왜 데이터 홈인가.** PM 데이터에는 내부 메모, 위험, 고객사 평가가 들어간다. 고객사 저장소에 두면 공동작업자에게 보이고, 프로젝트마다 흩어진다. 데이터 홈은 프로젝트 여러 개를 한 대시보드로 모으고, 원하면 그 폴더만 비공개 git으로 백업해 여러 PC에서 쓸 수 있다.
- **왜 의존성 없는 Node인가.** 외주 프로젝트마다 런타임과 패키지 관리자가 다르다. Node만 있으면 어느 프로젝트에서나 같은 명령이 돈다.

## 5. 화면 구성 (대시보드)

| 화면 | 답하는 질문 | 구성 |
|---|---|---|
| 오늘 | 지금 상태와 오늘 할 일 | 리미 브리핑, 핵심 숫자, 출시 D-day·처리/유입·킥오프 준비·고객사 대기, 전체 일정, 결정 필요, 고객사 답 대기, 이번 스프린트, 위험과 대응 |
| 킥오프 체크리스트 | 무엇이 있고 무엇이 없나 | 분류별 준비율, 상태 필터, 항목 표(상태·공·리소스·대기·막는 일정), 항목 서랍(확보 절차) |
| 일정·속도 | 언제 끝나고 무엇을 바꿔야 하나 | 예측 띠, 남은 이슈 추이, 가정해 보기, 스프린트, 주간 흐름 |
| 이슈 | 누구에게 몰렸고 무엇이 오래됐나 | 담당자별, 고객사·논의 대기 라벨, 2주 넘은 이슈, 표 |
| 리소스·연결 | 원본이 어디 있나 | SRS 카드(생성·보완 도우미), 연결 상태, 리소스 링크 |

상태 표시는 색만 쓰지 않고 아이콘과 글자를 같이 쓴다. 라이트·다크, 모바일 폭을 지원한다.

## 6. 핵심 흐름

### 6.1 없는 자료 확보 (예: 환불 정책)

1. 체크리스트에서 '없음' 항목을 고른다(대화: "환불 정책 없는데 어떻게 해?").
2. **받을 곳**: 고객 요청 DB(기본) · 공유 드라이브 · 이메일 · 저장소 문서.
3. **진행 방식**: 고객사에 요청 · 우리가 (제안) 초안을 쓰고 확인 · 회의 안건. 정책 문서는 초안 방식을 권한다.
4. 요청서가 써진다: 필요한 이유(막는 일정), 필요한 내용, (제안) 값, 전달 방법, 회신 기한.
5. 승인 대기열 → 사람이 발송 → '발송했음' → 상태 '요청함', 대기 일수 시작.
6. D+7이 넘으면 리마인드 초안. 리마인드에는 답이 없을 때 진행할 (제안) 값을 넣는다.

### 6.2 SRS 생성·보완

근거 자료(계약 범위, 회의록, 화면 설계, 이슈, 정책 항목)로 9개 절 초안을 만들고, 줄마다 확정·확인 요청·제안·준비 필요를 붙인다. 확인 요청 줄만 모아 고객 확인 요청서를 만든다. SRS가 있으면 빠진 절과 이슈·SRS 불일치를 찾는다. 대화(스킬)에서는 문서 파일로, 대시보드에서는 도우미 화면으로 만든다.

### 6.3 일정 예측

최근 4주(7일 구간) 가중 평균으로 처리와 유입을 구하고, 예상일(±40%), 목표일에 남을 양, 필요 처리량을 낸다. 가정(처리 ±%, 유입 ±%, 범위 −n건)을 바꿔 다시 계산한다. 자세한 식은 `skills/pm/references/forecast.md`.

### 6.4 고객사 공유본

`pm build --client`는 내부 메모(`internal`), 기록, 결정, 위험, 팀, 승인 대기열, 이슈 제목을 **데이터에서 빼고** 만든다. 화면도 공유 보기로 고정되고 일정 예측·이슈 화면이 없다. 화면에서 숨기기만 하는 방식과 달리, 파일을 열어 봐도 내부 정보가 없다.

## 7. 리미 — 대시보드의 에이전트 캐릭터

- **모습.** 리트머스 시험지. 몸의 색은 프로젝트 상태(파랑 순항, 보라 주의, 빨강 위험), 물든 높이는 진행률. 위험이면 걱정하는 표정과 땀방울.
- **위치.** 오늘 화면의 브리핑 카드, 오른쪽 아래 상주 버튼(상태와 신호 수, 기한 지난 대기가 있으면 빨간 점), 대화창.
- **내장 모드.** 키 없이 대시보드 데이터로 답한다: 브리핑, 일정(맞추려면 무엇을), 고객사 대기와 리마인드 묶음, 항목별 확보 절차, SRS, 위험, 담당자별 이슈.
- **Claude 모드.** 도구 6개(`get_dashboard`, `run_scenario`, `list_issues`, `draft_client_request`, `open_view`, `open_srs_wizard`)로 대시보드를 읽고 조작한다. `pm serve`를 띄운 셸에 `ANTHROPIC_API_KEY`가 있으면 서버를 거쳐 호출하고(키가 브라우저에 없음), 없으면 사용자가 화면에 넣은 키로 브라우저에서 직접 호출한다.
- **권한 경계.** 읽기, 계산, 화면 열기, 초안 쓰기만. 발송과 이슈 쓰기는 하지 않는다.

Claude Code에서는 스킬이 같은 원칙으로 일한다. 대시보드의 리미와 Claude Code는 같은 project.json을 본다.

## 8. 로컬 서버(`pm serve`)

- 127.0.0.1에만 열린다.
- 쓰기 요청은 같은 출처의 JSON만 받는다(다른 사이트가 로컬 서버에 쓰는 것을 막음).
- 체크리스트 항목은 정해진 필드(status, ball, res, requested, due, updated, receiveAt, mode, note)만 바꾼다. 파일은 임시 파일에 쓴 뒤 바꿔치기한다.
- `/api/claude`는 `ANTHROPIC_API_KEY`가 있을 때만 동작한다.

## 9. 단계

1. **지금 (0.1)**: 스킬 + CLI + 대시보드(정적·로컬 서버·고객사 공유본) + 표준 체크리스트. 사용자 PC 하나에서 여러 프로젝트.
2. **팀 공유**: 데이터 홈을 비공개 git 저장소로 두고 팀이 같이 쓰기, 매일 `pm sync`를 예약 실행, 메신저 진행상황 카드에 대시보드 링크.
3. **연동**: Notion 요청 DB에서 항목 상태와 고객 답 읽기, 승인한 요청서를 요청 DB 항목으로 만들기.
4. **포트폴리오**: 여러 프로젝트의 건강도를 한 화면에서 비교, 프로젝트 종류별 체크리스트 템플릿.

## 10. 한계

- 체크리스트 상태는 사람이(또는 Claude가) 고친다. 고객 소통 도구와 자동 연동은 아직 없다.
- 예측은 이슈 수로 센다. 이슈 크기가 크게 다르면 틀린다.
- `pm build`로 만든 파일에서 바꾼 상태는 그 브라우저에만 남는다. 계속 쓸 거면 `pm serve`.
- 리미의 Claude 모드는 실제 키로 대화까지 검증하지 않았다(요청 경로와 실패 시 내장 모드 전환만 확인).
