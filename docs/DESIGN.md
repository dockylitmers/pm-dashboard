# 설계 — 외주 개발 PM 시스템

외주 개발 PM이 프로젝트를 시작해서 출시할 때까지 쓰는 도구다. PM이 어떤 프로젝트를 하든 대시보드만 보면 실제 업무 상황을 알 수 있게 하는 것이 목표다. Claude Code 스킬(대화), CLI(기록·계산), 대시보드(한눈에 보기) 세 면이 PM 워크스페이스 하나를 같이 읽고 쓴다.

구조도 세 장(구성, Notion 연결, 업데이트)은 [docs/diagrams/](diagrams/)에 있다. PNG는 README에 들어가고, HTML을 브라우저로 열면 상자마다 근거 코드 위치로 갈 수 있다.

## 1. 풀려는 문제

외주 프로젝트의 일정은 개발 속도만으로 정해지지 않는다.

- **처음 무엇을 해야 하는지 모른다.** 계약서에 검수·지연 책임이 비어 있고, 고객사에 무엇을 언제 요청해야 하는지 모른 채 개발이 시작된다.
- **지연의 상당 부분이 고객사 대기에서 생긴다.** PG 라이브 상점, Apple 법인 계정, 발신번호, 공급사 운영 키처럼 준비에 몇 주 걸리는 것을 늦게 요청한다.
- **요청이 흩어지고 빈칸으로 나간다.** 메신저·메일·회의로 흩어진 요청은 근거가 남지 않고, 빈칸 질문은 왕복을 늘린다.
- **일정 예측이 감에 의존한다.** 처리 속도와 새 이슈 유입을 나눠 보지 않으면 "다음 주면 끝난다"가 반복된다.
- **정보가 흩어져 있다.** 이슈는 GitHub, 고객사 답은 Notion, 보고는 메신저, 계약은 공유 폴더.
- **한 번 채운 값은 낡는다.** 고객사 답, 결정, 콘솔 설정은 대시보드 밖에서 바뀐다. 언제 어디서 확인한 값인지 모르면 오래된 값으로 보고한다. 문서에 없다고 '없음'으로 적은 값이 실제로는 계정·통화로 이미 처리된 경우도 많다.

## 2. 목표와 비목표

| 목표 | 어디서 |
|---|---|
| 처음 쓰는 PM도 저장소 하나 만들고 세팅하면 모든 프로젝트를 같은 방식으로 관리한다 | `pm setup`, PM 워크스페이스 |
| 킥오프에 해야 할 일이 순서와 날짜로 나온다 | 킥오프 4단계, 이번 주 할 일 |
| 개발 범위를 정하면 고객사에 안내할 요청 목록이 나오고, 답이 같은 곳에 모인다 | 고객사 확인 요청 목록 |
| 계약서에서 놓치기 쉬운 것을 점검하고 대금을 검수와 연결해 추적한다 | 계약 점검 |
| 완료일을 범위로 예측하고, 맞추려면 무엇을 바꿔야 하는지 숫자로 본다 | 일정·속도, `pm forecast` |
| 대시보드가 실제 상황을 반영한다. 값마다 언제·어디서 확인했는지 보이고, 다시 볼 값이 저절로 모이고, 원본에서 바뀐 값이 하루 3번 반영된다 | 확인일·출처(`checked`), 업데이트(빠른·전체, 버튼·자동 실행), 최신화(`pm refresh`·`pm check`) |
| 고객사와 같은 화면을 본다 | 고객사 공유본 |

**비목표**: 이슈 트래커·고객 소통 도구를 대체하지 않는다(원본은 각 도구에, 여기는 위치와 상태). 자동 발송하지 않는다. 원본(GitHub·Notion)에 자동으로 쓰지 않는다. 법률 자문을 하지 않는다.

## 3. 설계 원칙

1. **결론 먼저.** 맨 위에 브리핑, 숫자와 표는 그 아래.
2. **공(ball) 추적.** 모든 항목에 다음 행동을 할 쪽과 대기 일수(D+n).
3. **늦기 전에 요청한다.** 항목마다 필요 시점과 준비 기간 → 요청 시작일. 이 날이 지나면 '늦음'.
4. **빈칸 대신 (제안) 값.** 아는 값을 채우고 고객사는 확인만.
5. **원본은 한 곳.** 링크와 상태만, 내용은 복사하지 않는다. 고객 소통의 원본은 요청 DB.
6. **사람이 보낸다.** 초안까지만 자동. 외부 발송, GitHub·Notion 쓰기는 사용자 확인 뒤.
7. **같은 화면, 다른 깊이.** 고객사 공유본은 내부 데이터를 빼고 만든 같은 화면.
8. **비밀값은 받지 않는다.** 계정은 권한 초대로.
9. **고객사 저장소를 더럽히지 않는다.** PM 데이터는 PM 워크스페이스에.
10. **값에는 확인한 날과 출처가 붙는다.** 원본에서 찾지 못한 값은 '없음'으로 적지 않고 추정으로 둔다.
11. **업데이트는 원본을 읽기만 한다.** 빠른 업데이트는 다시 볼 값을 찾고, 전체 업데이트는 Claude가 원본을 읽어 이 워크스페이스의 값까지 고친다. 원본에는 쓰지 않고, 확인하지 못한 것은 추정으로 두고 PM에게 묻는다.

## 4. 구성

```
pm-dashboard (이 저장소, Claude Code 플러그인)
└─ skills/pm
   ├─ SKILL.md            Claude가 따르는 절차와 원칙
   ├─ references/         세팅·체크리스트·요청 목록·계약·SRS·예측·데이터 형식
   ├─ scripts/pm.mjs      CLI (Node 18+, 의존성 없음)
   │  └─ lib/             workspace·library·github·build·server·update·schedule·common
   ├─ app/                대시보드 (index.html + js/forecast·core·docs·app·agent)
   └─ templates/          항목 라이브러리(51개), 계약 점검(12개), 새 프로젝트 뼈대, 데모

PM 워크스페이스 (PM의 비공개 GitHub 저장소를 내려받은 폴더)
├─ pm-workspace.json             회사 이름, 자동 실행(schedule)·전체 업데이트(update) 설정
├─ projects/<id>/project.json    원본
├─ projects/<id>/docs/           요청 목록·킥오프 자료·주간 보고 초안
├─ projects/<id>/github.json     이슈 스냅샷 (git 제외)
├─ projects/<id>/update.json     마지막 업데이트 결과와 기록 (git 제외)
├─ .pm-logs/                     자동 업데이트·서버 기록 (git 제외)
└─ build/                        대시보드 파일 (git 제외)
```

```
PM ──대화──▶ Claude Code + 스킬 ──명령──▶ pm CLI ──읽기·쓰기──▶ project.json ──git──▶ PM 워크스페이스 저장소
                                              ├─ sync ──▶ GitHub 이슈·마일스톤
                                              ├─ update ──▶ GitHub 스냅샷 + 다시 확인할 값 ──▶ update.json
                                              │    └─ --deep ──▶ claude -p (읽기 도구 + pm CLI만) ──읽기──▶ GitHub 코멘트 · Notion 요청 페이지
                                              └─ setup-repo ──▶ GitHub 라벨·스프린트 (확인 뒤)
             Claude ──Notion 도구──▶ 고객 요청 DB (요청 목록 올리기·답 읽기, 확인 뒤)
launchd ──▶ pm update --all [--deep] (매일 08:30·12:30·18:30) · pm serve (상시)        ← pm schedule install
PM ──브라우저──▶ 대시보드 ◀── pm build(파일) / pm serve(로컬 서버, 변경 저장·업데이트 실행)
                  └─ 리미 ── 내장 모드 / Claude(serve의 ANTHROPIC_API_KEY)
고객사 ──브라우저──▶ 고객사 공유본 (pm build --client)
```

- **같은 계산을 쓴다.** `forecast.js`(예측), `core.js`(상태·요청 시작일·킥오프 단계·요청 목록·건강도·브리핑·요청서·확인일과 다시 확인할 값), `docs.js`(요청 목록·킥오프 자료·주간 보고)는 브라우저와 Node 양쪽에서 돈다.
- **왜 PM 워크스페이스 저장소인가.** PM 데이터에는 내부 메모·위험·계약이 들어가므로 고객사 저장소에 두면 안 된다. PM 한 사람의 비공개 저장소에 모으면 모든 프로젝트를 한 대시보드로 보고, git으로 PC 사이를 맞추고, 이력이 남는다. `pm setup`이 등록해 두므로 고객사 저장소 폴더에서 일해도 데이터는 워크스페이스로 간다.
- **왜 업데이트 결과는 따로 두나.** 업데이트의 결과와 기록은 `update.json`에 쓴다. 다시 만들 수 있는 것이라 git에서 뺀다. 빠른 업데이트는 `project.json`을 건드리지 않는다. 전체 업데이트도 `project.json`을 직접 고치지 않고 `pm answer`·`set`·`check`를 거친다. 사람이 고칠 때와 같은 검사를 지나고 확인일·출처가 남는다.
- **왜 전체 업데이트는 Claude Code headless인가.** 원본을 읽고 판단하는 일은 대화의 '최신화'와 같다. 같은 순서를 프롬프트로 주고, 이미 쓰는 도구(gh, Notion MCP)를 그대로 쓰되, 권한은 읽기 도구와 pm CLI로 좁힌다.
- **왜 의존성 없는 Node인가.** 외주 프로젝트마다 런타임과 패키지 관리자가 다르다. Node만 있으면 된다.

## 5. 처음 쓰는 PM의 흐름

1. 플러그인 설치 → GitHub에 비공개 저장소를 만들어 내려받기 → "PM 워크스페이스로 세팅해 줘"(`pm setup`). 공개 저장소면 경고한다.
2. "새 프로젝트 등록해 줘 …" — 이름, 고객사, 일정, **개발 범위**를 말하면 `pm init --scope`. 견적서를 주면 범위를 제안한다.
3. 킥오프 4단계를 따라간다. 대시보드·`pm kickoff`가 이번 주 할 일을 요청 시작일 순으로 보여 준다.
4. 첫 commit·push. 이후 바뀔 때마다 commit.
5. 전체 업데이트를 세팅한다. `pm doctor`로 점검(Claude Code 로그인, 사용자 범위 Notion MCP, GitHub 토큰, 프로젝트별 Notion 링크)하고 `pm schedule install --deep`(시각, 전체·빠른, 서버를 켜 둘지 확인 뒤). 이후 대시보드를 열면 하루 3번 원본까지 반영된 상태다.

대시보드도 프로젝트가 없으면 이 순서를 안내한다.

## 6. 킥오프

### 6.1 범위에서 항목으로

`templates/library.json`의 표준 항목 51개는 각각 `when`(필요한 기능), `needBy`(필요 시점), `leadDays`(준비 기간), `fields`(고객사에 물을 입력 칸과 제안값)를 가진다. 범위를 고르면 해당 항목만 체크리스트에 들어간다. 범위를 바꾸면 새 항목이 추가되고, 범위에서 빠진 항목은 아무 일도 없었을 때만 '해당 없음'이 된다.

**요청 시작일 = 필요 시점 − 준비 기간.** 필요 시점은 프로젝트 날짜에서 나온다(기능 개발 = 개발 기간 가운데, 스토어 제출 = 출시 2주 전). 이 날이 7일 안이면 ⭐, 지났는데 요청 전이면 '늦음'.

### 6.2 4단계

| 단계 | 끝 |
|---|---|
| 계약 확인 | 계약서·범위 기준선 확정 + 계약 점검 12항목 확인 |
| 범위·SRS | SRS·일정·검수 기준·변경 절차를 받음 이상 |
| 고객사 요청 | 요청 목록의 모든 항목을 보냄 |
| 기본 세팅 | 담당자·채널·보고 확정, 저장소·라벨·스프린트 |

'이번 주 할 일'은 요청 시작일이 지났거나 7일 안인 항목, D+7이 넘은 대기, 검토할 답, 다시 확인할 값, 남은 계약 점검, 저장소 세팅, 마감 지난 스프린트를 모은다.

### 6.3 계약 점검

범위 부속서, 검수 방법·기간, 대금 단계와 검수 연결, 변경 요청 비용, 고객사 지연 시 일정 순연, 산출물·소스·계정 인도, 지식재산권, 하자 보수, 유지보수, 제3자 비용, 개인정보 처리 위탁, 해지·정산. 상태는 있음·불리/모호·없음·해당 없음. 이미 서명했다면 위험 항목을 킥오프 회의의 합의로 보완한다(내부 준비 판에 모인다). 대금 단계(착수금·중도금·잔금)는 일정에 묶어 예정일을 계산하고 청구·수령을 기록한다.

### 6.4 기본 세팅

`pm setup-repo`가 일정 예측이 읽는 규칙대로 라벨(epic, descope, 확인요청, blocked)과 주 단위 스프린트(`SP-01 · 10/26~10/30`), 고객사 QA, 출시 마일스톤을 계획하고, 확인 뒤 만든다. 소통 채널(요청 DB), 보고 방식(주간 보고·격주 회의)은 요청 목록의 항목으로 고객사와 합의한다.

### 6.5 킥오프 회의 자료

개요(범위), 일정, 소통·보고 방식, 검수와 변경 관리, 고객사에 요청할 것(회신 기한 순, ⭐), 첫 2주 계획, 회의에서 정할 것. 내부 판에는 계약 점검 위험·대금·위험·결정이 더해진다.

## 7. 고객사 확인 요청 목록

외주를 맡긴 고객사에게 "개발에 무엇이 필요한지"를 안내하고 답을 모으는 목록이다. 실제로 쓰던 Notion 요청 페이지의 방식을 그대로 따른다.

- 표 하나, 다섯 칸: 분야 | 항목 | 확인/요청 내용 | 정보 | 비고사항.
- **정보** 칸은 `• 라벨: 값` 입력 줄. 우리가 채운 제안값은 분홍, 고객사 답은 노랑. 제안값의 일정은 프로젝트 날짜로 채운다.
- 분야는 묶음 첫 줄에만, 먼저 필요한 묶음에 ⭐. 답을 아직 받지 않은 줄의 비고에 회신 기한.
- 처음 보낸 뒤의 추가 요청은 같은 표에 '추가 확인 요청 (M/D)' 구분 줄로 이어 붙인다(차수 = 요청일).
- 계정은 비밀번호 대신 권한 초대 이메일과 2단계 인증 담당자를 묻는다. 기존 페이지에서 비밀번호를 그대로 받던 문제를 템플릿에서 막는다.

형식: Markdown(붙여 넣기용), Notion enhanced markdown(Claude가 Notion 도구로 요청 페이지를 만들 때, `pink_bg`·`yellow_bg`). 보낸 뒤 '보낸 것으로 표시' → 대기 일수 시작. 답은 대시보드에서 항목을 눌러 적거나 `pm answer`, 또는 Claude가 Notion의 노랑 답을 읽어 와 기록한다. 어느 쪽이든 답을 기록하면 확인일과 출처가 함께 남는다.

고객사 공유본의 첫 화면이 이 목록('개발 관련 요청사항')이다. 보낸 항목만 나오고, 무엇을 빼는지는 10장의 공유본 규칙을 따른다.

## 8. 진행 중

- **브리핑**(터미널 `pm status`·리미): 기한 지난 결정 → 킥오프 단계 → 리마인드할 고객사 대기(필요일 지남·7일 넘게 답 없음) → 일정 예측 → 먼저 요청할 것 → 마감 지난 스프린트 → 다시 확인할 값 → 다가오는 결정, 최대 5줄.
- **오늘 먼저 할 것**(홈 상태 카드): 지금 바로 할 행동 1~3개와 버튼. 기한 지난 결정 → 리마인드 → 요청 늦은 자료 → 지난 스프린트 → 기한 지난 위험 → 받은 자료 검토 → 다시 확인할 값 순으로 고른다. 첫 행동이 화면의 기본 버튼이다.
- **늦음은 두 말로**: '필요일 지남'(항목이 막는 일정의 날짜가 지남)과 '7일 넘게 답 없음'(요청한 날부터 센 대기). 할 일에는 이 밖에 '기한 지남'(결정·위험), '요청 시작일 지남', '마감 지남'(스프린트)이 이유로 붙는다. 할 일은 필요일·기한 하나로 정렬한다.
- **결정·위험의 기한**은 날짜로 저장한다(`pm decision`·`pm risk`가 '오늘'·'이번 주'를 쓰는 날 기준 날짜로 바꾼다). 화면은 'D-2'·'2일 지남'으로 계산하고, 결정·위험에도 체크리스트처럼 확인일(`checked`)이 붙는다.
- **일정 예측**: 최근 4주(7일 구간) 가중 평균으로 처리·유입, 예상일 ±40%, 목표일에 남을 양, 필요 처리량. 가정(처리·유입·범위)을 바꿔 다시 계산. 자세한 식은 `skills/pm/references/forecast.md`.
- **주간 보고**: 팀용(속도·위험·결정 포함)과 고객사용(진행률·다음 주·고객사 확인 필요).
- **최신화와 업데이트**: 9장.

## 9. 최신화와 업데이트

대시보드가 실제와 맞으려면 두 가지가 필요하다. 값마다 언제·어디서 확인했는지 남기는 것, 그리고 다시 볼 값을 때맞춰 찾아 원본과 대조하는 것.

### 9.1 확인일과 출처

체크리스트 항목마다 `checked: { at, src, guess? }`가 있다. 마지막으로 원본에서 확인한 날, 확인한 곳, 추정 여부다.

- 고치는 곳: `pm answer --src`, `pm set --src`(`--guess`), `pm check <item...> --src`(값이 그대로일 때 확인일만 새로), 대시보드 항목의 '지금 확인함'과 상태 저장. 대시보드에서 저장하면 그날 확인한 것으로 남고 추정 표시가 지워진다.
- 확인일(`checkedAt`)은 `checked.at`·`answeredAt`·`updated` 중 가장 늦은 날이다. `checked`가 없던 예전 항목도 확인일을 가진다.
- 화면: 킥오프 체크리스트의 항목마다 '확인 M/D · 출처'와 추정·오래됨 표시, 항목 상세의 '최근 확인'.
- 원본에서 찾지 못한 값은 '없음'으로 적지 않고 `--guess`로 추정 표시한다. 기록이 없다고 없는 것이 아니다.

### 9.2 다시 확인할 값

| 구분 | 기준 | 계산하는 곳 |
|---|---|---|
| 추정 | `checked.guess` | `core.js` (브라우저·Node) |
| 오래됨 | 확정·해당 없음이 아닌 항목을 14일 넘게 확인하지 않음. 아직 손대지 않은 '없음' 항목은 빼고 요청 시작일로 챙긴다 | `core.js` |
| 확인 뒤 GitHub 이슈가 바뀜 | 항목의 원본 링크·메모(`res`, `note`, `internal`)에 적힌 GitHub 이슈 링크나 `#번호`의 갱신 시각이 확인일보다 늦음 | `pm refresh`, `pm update` (GitHub 조회) |

추정과 오래됨은 화면에서 바로 계산되어 킥오프 체크리스트의 '다시 확인' 거르기, 브리핑 머리의 기준 시각 줄, 할 일에 나온다. GitHub 조회가 필요한 세 번째 구분은 `pm refresh`와 업데이트 창에 나온다.

### 9.3 업데이트

업데이트는 사람 없이 도는 부분이다. 두 가지가 있다.

| 업데이트 | 하는 일 | 걸리는 시간 |
|---|---|---|
| 빠른 (`pm update`) | 프로젝트마다 GitHub 이슈·마일스톤 스냅샷을 새로 받고(`pm sync`와 같다), 다시 확인할 값을 계산한다 | 몇 초 |
| 전체 (`pm update --deep`) | 빠른 업데이트를 한 뒤, Claude가 원본을 읽고 이 워크스페이스의 값을 고친다(9.4). 못 찾은 값은 추정으로 두고 '답해 주실 것'(asks)으로 남긴다 | 몇 분. Claude 사용량이 든다 |

어느 쪽도 원본(GitHub·Notion)에는 쓰지 않는다.

- **update.json**: `{ last: { at, mode, trigger, ok, durationSec, steps, recheck, recheckItems, summary, changed, asks, cost, error }, history }`. `mode`는 `quick`·`deep`, `trigger`는 `manual`(터미널)·`dashboard`·`schedule`. `changed`(바뀐 값)·`asks`(답해 주실 것)·`cost`는 전체 업데이트일 때만 채워진다. 기록은 30개까지. 형식은 `skills/pm/references/data-model.md`.
- **한 번에 하나.** 워크스페이스의 `.pm-update.lock`으로 동시에 돌지 않게 한다. 실행 중이면 다음 요청은 거절된다. 45분 넘은 잠금은 무시한다.
- **대시보드 버튼.** 상단 '업데이트 오늘 HH:MM · 답할 것 N'에 마지막 업데이트 시각과 답할 것 개수가 나온다. 12시간이 넘었거나 마지막 업데이트가 실패했으면 글자가 주의 색이 된다. 누르면 '원본에서 다시 읽기' 창이 열린다: 자동 업데이트 상태(시각, 전체·빠른), '빠른 업데이트'·'전체 업데이트' 버튼, 마지막 업데이트(언제, 누가, 전체·빠른, 걸린 시간, 단계별 결과), 전체 업데이트의 요약·'답해 주실 것 N개'·'이번에 바뀐 값 N개', 다시 확인할 값 목록(추정·GitHub 바뀜·오래됨), 기록.
- **버튼은 `pm serve`에서만.** 서버가 `pm update [--deep]`을 별도 프로세스로 띄우고(`POST /api/update`, 실행 중이면 409), 화면은 2초마다 `GET /api/update`로 상태를 보다가 끝나면 페이지를 다시 받는다. '전체 업데이트' 버튼은 서버가 이 PC에서 claude를 찾을 때만 보인다(`deepReady`). `pm build` 파일에는 만들 때의 기록만 들어간다.

**자동 실행(`pm schedule`).** `pm schedule install [--deep]`은 macOS launchd 사용자 에이전트 둘을 만든다.

| 에이전트 | 하는 일 |
|---|---|
| `com.pm-dashboard.update` | 매일 정한 시각(기본 08:30·12:30·18:30, `--times`로 변경)에 `pm update --all`, `--deep`이면 전체 업데이트 |
| `com.pm-dashboard.serve` | 대시보드 서버(127.0.0.1:4477)를 로그인 동안 계속 켜 둔다. `--no-serve`면 만들지 않는다 |

- `--deep`이면 먼저 `pm doctor`와 같은 점검을 하고, 빠진 것이 있으면 빠른 업데이트로 켠다.
- 플러그인은 버전마다 설치 폴더가 바뀌므로, 설정 폴더의 실행 스크립트(`pm-run.sh`)가 실행할 때 가장 새 버전을 찾는다. launchd는 PATH가 짧고 셸 설정이 없어 node·gh·git·claude가 있는 폴더를 넣고, 설치할 때 찾은 claude 경로를 `PM_CLAUDE_BIN`으로 고정한다.
- 기록은 `<워크스페이스>/.pm-logs/`(update.log, serve.log), 설정은 `pm-workspace.json`의 `schedule`(`{ times, deep, serve, installedAt }`)에 남는다.
- 이 PC의 자동 실행은 하나다. 다른 워크스페이스에 등록돼 있으면 `pm schedule`이 알려 준다.
- Mac이 잠자기 중이면 그 시각은 건너뛰고 깨어난 뒤 한 번 실행된다. 다른 OS에서는 등록하지 않고 cron 줄을 보여 준다.
- 상태는 `pm schedule`, 끄기는 `pm schedule remove`. 설치 전에 Claude가 시각, 전체·빠른, 서버를 켜 둘지 확인한다.

### 9.4 전체 업데이트 (Claude)

`pm update --deep`은 빠른 업데이트 뒤 프로젝트마다 Claude Code를 headless로 띄운다(`claude -p --output-format json --permission-mode dontAsk --no-session-persistence`, 프롬프트는 stdin). 샘플 프로젝트는 건너뛰고, 25분이 넘으면 끊는다.

지시문만 믿지 않는다. 전체 업데이트가 도는 동안에는 CLI가 지우거나 되돌리기 어려운 변경을 거절한다: `decision done`, `risk remove`, `scope` 변경, `sheet --mark-sent`, `contract` 변경, `setup-repo --apply`(GitHub 쓰기), `--out` 파일 쓰기, `init`·`setup`·`schedule`·`config` 변경, `install-cli`. 전체 업데이트의 Claude가 부르는 CLI(`PM_DEEP_UPDATE=1`)와, 같은 워크스페이스에 전체 업데이트 잠금(`.pm-update.lock`, mode deep, 프로세스가 살아 있을 때)이 있는 동안 PM이 직접 치는 명령 모두에 해당한다. PM은 몇 분 뒤 끝난 다음 다시 하면 된다. 프로세스가 없는 오래된 잠금은 무시한다. 값을 고치는 `answer`·`set`·`check`·`decision set/check`·`risk set/check`는 그대로 된다. 확인은 인자 모양이 아니라 실제로 실행될 동작 바로 앞에서 한다(`pm.mjs`의 `guardDeep`).

프롬프트가 시키는 일:

1. `refresh --json`과 `list --json`으로 다시 확인할 항목과 전체 항목을 본다.
2. 원본을 읽기만 한다. GitHub은 확인일 뒤의 이슈 코멘트(특히 결정 코멘트), Notion은 고객 소통 페이지와 항목의 `res.url`(노랑 답과 댓글), 도메인은 `dig`. 항목이 많으면 오래된 것과 GitHub 이슈가 바뀐 것부터 30개까지.
3. 반영은 pm CLI로만 한다. 바뀐 값은 `answer`·`set --src`, 그대로면 `check --src`, 확인하지 못한 값은 `check --guess`로 두고 asks에 질문을 넣는다.
4. 비밀번호·키·개인 연락처는 기록하지 않는다. 고객사가 보는 칸(note·fields 등)은 결론만 쓰고 이슈 번호·사람 이름은 `internal`에 쓴다. 확정은 원본에 근거가 있을 때만.
5. 마지막에 `{ summary, changed, asks }` JSON 하나를 낸다. 이것과 비용이 `update.json`에 남는다.

**권한.** 허용하는 도구는 `Bash(node <pm.mjs> *)`, `gh issue view·list`, `gh pr view·list`, `dig`, Read·Grep·Glob, Notion fetch·search·get-comments뿐이다. Edit·Write·NotebookEdit·WebFetch·WebSearch는 막고, 그 밖의 도구는 `dontAsk` 모드라 묻지 않고 거절된다. 원본에 쓰는 도구는 없다. `pm-workspace.json`의 `update`로 읽기 도구를 더하거나(`allowedTools`, 예: 사내 시스템의 조회 도구), 모델(`model`)과 한 번에 쓸 비용 한도(`maxBudgetUsd`)를 정한다.

**준비(`pm doctor`).** 빠진 것마다 할 일을 알려 준다.

| 점검 | 갖출 것 |
|---|---|
| Claude Code | 설치와 로그인. claude는 `PM_CLAUDE_BIN` → PATH → 로그인 셸 순으로 찾는다 |
| Notion 연결 | 사용자 범위 Notion MCP: `claude mcp add --scope user --transport http notion https://mcp.notion.com/mcp` → `claude` 실행 → `/mcp`에서 인증. 특정 폴더(local 범위)에만 등록돼 있으면 워크스페이스에서 돌 때 보이지 않는다 |
| GitHub 로그인 | `gh auth login` 또는 `GITHUB_TOKEN` |
| 프로젝트 원본 (경고) | 프로젝트마다 `channels.notion.url`(고객 요청 DB 링크). 없으면 Claude가 어디를 읽을지 모른다 |

`pm update --deep`은 시작 전에 Claude Code와 GitHub 로그인을 점검하고, 없으면 시작하지 않는다.

### 9.5 업데이트 상태를 보이는 법

- `update.json`의 `last.sources`에 원본별 마지막 성공 시각(`github`, `client`)을 남긴다. 전체 업데이트가 Claude 단계에서 실패하면 GitHub는 새 시각, 고객사 답은 앞의 시각이 남는다. 화면은 이 둘을 따로 보인다('GitHub 08:30 · 고객사 답 10/13 18:34').
- 상단 버튼은 실패면 '업데이트 일부 실패', 12시간 넘게 업데이트가 없으면 'N시간 전'을 경고 아이콘과 함께 보인다. 색만으로 알리지 않는다.
- 실패 원문(영어 오류 등)은 '무엇을 못 읽었는지 · 왜 · 언제 다시'의 쉬운 말로 바꿔 보이고(`core.js`의 `explainStep`), 원문은 접어 둔다. 기록에서도 실패한 실행은 표시한다.

### 9.6 대화로 최신화

전체 업데이트를 켜지 않았거나 지금 바로 맞출 때는 PM이 "최신화해 줘"라고 하고, Claude가 같은 순서를 대화로 한다. 전체 업데이트가 남긴 '답해 주실 것'은 다음 대화에서 한 번에 묻는다.

1. `pm refresh`(`--json`이면 이슈 상태까지)로 다시 볼 값을 모은다.
2. GitHub 이슈가 바뀐 항목은 확인일 뒤의 이슈 코멘트를 읽는다.
3. Notion 등 고객 소통 원본이 출처인 항목은 그 페이지의 고객사 답(노랑)과 댓글을 읽는다.
4. 직접 볼 수 있는 것(도메인 DNS, 공개 URL, 스토어 등록 상태 등)은 읽기만 해서 확인한다.
5. 바뀐 값은 `pm answer`·`pm set --src`로, 그대로인 값은 `pm check --src`로 기록한다.
6. 남은 추정 값과 사용자만 아는 것(콘솔, 계약, 통화)은 지금 값·찾아본 곳과 함께 한 번에 묻고, 답은 `--src "PM"`으로 기록한다.
7. 바뀐 것, 아직 모르는 것, 그 때문에 막히는 일정을 보고한다.

상단에는 프로젝트 선택, 상태, 출시 D-day, '업데이트'(9.3), '승인 대기', '고객사 공유 보기'가 있다. 탭 제목은 워크스페이스 회사 이름을 따른다('<회사> PM 대시보드', 공유본은 '<회사> 개발 관련 요청사항').

**고객사 공유본(`pm build --client`)**: 화면은 '오늘'과 '고객사 요청'(제목 '개발 관련 요청사항', 보낸 항목만)이고, 내부 정보는 화면에서 숨기지 않고 데이터에서 뺀다.

- 프로젝트에서 결정·위험·팀·승인 대기열·메모·계약을 뺀다.
- 체크리스트 항목에서 내부 메모(`internal`), 기록(`history`), 확인 기록(`checked`)을 뺀다.
- 출처 링크(`res`)는 Notion 링크만 남긴다. GitHub 이슈·저장소 문서 경로는 내부 정보라 뺀다.
- 이슈 스냅샷은 제목 없이 마일스톤 진행률만 넣는다. 업데이트 기록과 자동 실행 설정은 넣지 않고, 업데이트 버튼과 리미도 없다.

내부 대시보드의 '고객사 공유 보기'는 같은 모습을 미리 보는 토글이다(이때는 화면에서 숨긴다).

**화면 규칙**: 초록·주황·빨강은 상태(순항·주의·위험, 늦음)에만 쓴다. '오늘' 선은 중립색, 마감 표식은 검정. 보조 글자도 배경·지표 타일·다크 배경에서 4.5:1 이상. 닫힌 서랍은 `inert`라 Tab이 들어가지 않고, 열린 서랍·모달은 포커스를 가둔다. 1400px 이하에서는 상단 바를 한 줄로(보조 버튼은 아이콘), 휴대폰에서는 보조 버튼을 '더보기' 메뉴로, 카드 순서를 상태 → 할 일 → 예측으로 바꾼다. 프로젝트 고르기 목록에는 프로젝트마다 상태와 출시 D-day를 붙인다(포트폴리오 화면은 11장 4단계).

**리미**: 리트머스 시험지 모양의 에이전트. 색 = 상태(초록 순항·주황 주의·빨강 위험, 상태 칩과 같은 색), 물든 높이 = 진행률. 말풍선은 처음 들어왔을 때만 보이고 스크롤하면 아바타만 남는다. 내장 모드는 대시보드 데이터로 답하고(킥오프, 요청 목록, 계약, 주간 보고, 회의 자료, 일정, 대기, 위험), Claude 모드는 도구 7개로 대시보드를 읽고 문서를 만든다. 읽기·계산·화면 열기·초안까지만 한다.

**로컬 서버(`pm serve`)**: 127.0.0.1에만 열고, 쓰기는 같은 출처의 JSON 요청만 받는다. 체크리스트는 정해진 필드와 입력 칸 답, 확인 기록만, 계약은 점검 상태와 대금 상태만 바꾼다. 업데이트는 `/api/update`로 시작하고 상태를 본다(9.3). 파일은 임시 파일에 쓴 뒤 바꿔치기한다. 포트를 이미 쓰고 있으면, 같은 워크스페이스의 대시보드 서버(자동 실행이 켜 둔 것)는 새로 띄우지 않고 그것을 연다. 다른 워크스페이스나 다른 프로그램이면 `--port`를 쓰라고 알린다.

## 11. 단계

1. **지금 (0.8)**: PM 워크스페이스, 범위 기반 항목·요청 목록, 킥오프 4단계, 계약 점검, 저장소 세팅, 회의 자료·주간 보고, 대시보드·고객사 공유본, 확인일·출처와 다시 확인할 값, 업데이트(빠른·전체, 버튼·`pm update`·하루 3번 자동 실행), `pm doctor`, 결정·위험의 날짜 기한과 확인일, 원본별 기준 시각과 실패 안내, 홈의 '오늘 먼저 할 것'.
2. **팀**: 팀 PM 여러 명이 같은 워크스페이스 저장소를 쓰는 규칙(프로젝트 담당자), 주간 보고 예약 발송(GitHub Actions → 메신저).
3. **연동**: 요청 DB에 항목 상태 쓰기(지금은 읽기만), 견적서에서 범위 자동 추출.
4. **포트폴리오**: 여러 프로젝트의 건강도·대금·고객사 대기를 한 화면에서 비교. 지금(0.8)은 프로젝트 고르기 목록에 상태와 출시 D-day만 붙인다.

## 12. 한계

- 업데이트는 원본에 쓰지 않는다. 요청 DB의 상태와 고객사에 보내는 글은 여전히 사람이 다룬다.
- 전체 업데이트의 반영은 Claude의 판단이다. 근거가 약하면 바꾸지 않고 추정·질문으로 남기지만, '이번에 바뀐 값'은 PM이 확인한다.
- 전체 업데이트는 돌 때마다 Claude 사용량이 들고, 한 번에 항목 30개까지 본다. 이 PC에 Claude Code와 사용자 범위 Notion MCP가 있어야 한다.
- '확인 뒤 GitHub 이슈가 바뀜'은 항목에 이슈 링크나 `#번호`가 적혀 있어야 잡힌다.
- 자동 실행은 macOS에서만 등록한다. PC가 꺼져 있거나 로그인하지 않은 동안은 돌지 않는다.
- 예측은 이슈 수로 센다. 이슈 크기가 크게 다르면 틀린다.
- `pm build` 파일에서 바꾼 상태는 그 브라우저에만 남고, 업데이트도 할 수 없다. 계속 쓸 거면 `pm serve`.
- 계약 점검은 체크리스트이고 법률 검토를 대신하지 않는다.
- 리미의 Claude 모드는 실제 키로 대화까지 검증하지 않았다.
